## 1. INTRODUCTION

### 1.1 Purpose of the Document

This D7 document describes the testing phase of R Mall, a cloud-based small e-commerce platform developed for a Network Technology Final Year Project. The purpose of this document is to show that the system implemented in D6 has been tested for functional correctness, integration readiness, cloud deployment readiness, and network performance.

This document explains the testing plan, test basis, selected testing techniques, test case design, testing execution, testing results, unexpected problems, and testing summary. The evidence is taken from source code, automated verification scripts, deployment records, JMeter execution records, JMeter result summaries, D5, and D6.

### 1.2 Scope of the Document

The scope of this document covers testing for R Mall as implemented with Vue 2, Spring Boot, MySQL, Redis, Nginx, and Google Cloud VM deployment. The testing focuses on the main user and system workflows:

- user registration and login;
- email verification for registration and password reset;
- homepage, product list, and product detail browsing;
- cart management;
- order placement;
- simulated payment;
- order history;
- basic administrator functions;
- cloud deployment and public HTTP access; and
- network performance measurement using Apache JMeter.

This document does not cover real payment gateway testing, real logistics testing, full penetration testing, commercial security certification, HTTP-versus-HTTPS comparison, Kubernetes testing, autoscaling testing, or commercial traffic-capacity certification. These exclusions are consistent with the project scope in D5 and the implemented system boundary in D6. R Mall is evaluated as an academic cloud-based e-commerce prototype, not as a commercial production platform.

### 1.3 Terms, Acronyms and Abbreviations

| Term / Acronym | Meaning |
|---|---|
| API | Application Programming Interface. In this project, API refers to Spring Boot REST endpoints called by Vue and JMeter. |

| Smoke testing | A small initial test used to confirm that a function or test plan can run before heavier testing. |
| Throughput | Number of completed requests or samples per second. |
| VM | Virtual Machine. The deployed system runs on a Google Cloud VM. |

### 2.3 Testing Approach and Test Design Techniques

The selected testing approach combines white-box testing, black-box testing, regression testing, integration testing, deployment testing, basic security testing, and performance testing. This approach is suitable because the project has two main responsibilities: the e-commerce system must function correctly, and its network behaviour must be measurable under concurrent user load.

**Table 2.3: Testing Types Used**

| Testing type | Category | Reason for selection |
|---|---|---|
| Unit testing | White-box / component | Used to verify code-level behaviour such as Redis TTL, email cooldown, wrong-code rejection, email registration, and password reset. |
| Integration testing | Functional | Used to verify that Vue, Spring Boot, Redis, MySQL, and Nginx interact through the expected paths. |
| Regression testing | Functional | Used to confirm that changes to authentication, routes, deployment configuration, and database schema do not break existing behaviour. |
| Black-box testing | Functional | Used by JMeter because requests are sent through the public endpoint and judged by external response behaviour. |
| Connectivity / deployment testing | Non-functional | Suitable for the Network Technology track because the system must prove the HTTP, Nginx, Spring Boot, MySQL, and Redis path. |
| Basic security testing | Non-functional | Used to verify session control, expired-token handling, protected routes, and email-code cooldown. This is not a full penetration test. |
| Performance and load testing | Non-functional | Used to measure response time, P90, throughput, and error rate under different JMeter thread levels. |
| Controlled mutation testing | Functional and performance | Used to evaluate write operations such as add-to-cart, place-order, and simulated-payment while limiting demo-data impact. |

## 4. TESTING

### 4.1 Test Execution Procedure

The official retained testing evidence was executed on 16 June 2026. Testing was performed in stages so the system was not placed under high load before basic readiness was confirmed. The execution sequence was:

1. Prepare Apache JMeter 5.6.3 locally.
2. Verify the SHA512 checksum for the downloaded JMeter package.
3. Validate all `.jmx` files using `xmllint`.
4. Parameterize JMeter plans so `THREADS`, `RAMP_UP`, and `LOOPS` can be controlled through CLI execution.
5. Add sampler assertions so business responses are checked.
6. Run one-user smoke tests for all eight JMeter plans.
7. Create a VM-side MySQL backup before mutation tests.
8. Record baseline values for `t_order`, `cart`, and selected product stock.
9. Check VM service health before load tests.
10. Run the read-only load matrix.
11. Check VM service health after read-only tests.
12. Run the authenticated load matrix.
13. Check VM service health after authenticated tests.
14. Run controlled mutation tests.
15. Record database impact after mutation tests.
16. Generate aggregate CSV, Markdown summary tables, and SVG charts.
17. Run final local and VM verification checks.

### 4.2 Functional and Regression Test Execution

Functional and regression testing was executed using Maven, npm, and Node.js scripts. Backend tests checked email verification, session behaviour, registration, login, and password reset. Frontend checks verified authentication wiring, route guards, deployment paths, and production build readiness. Database checks verified that the schema remained consistent with the project design.

The main commands used were:

mvn -q test

```bash

npm run build
```

```bash

```

### 4.3 Deployment Test Execution

Deployment testing was performed against the public URL:

```text
http://34.143.225.11/
```

The system is deployed on a Google Cloud VM with Nginx as the public entry point. Nginx serves the Vue static files and forwards `/api/` requests to Spring Boot at `127.0.0.1:9191`. MySQL and Redis run as supporting VM services. After each JMeter load phase, the main services were checked to ensure that the system remained stable.

### 4.4 Performance Test Execution

Performance testing was executed using Apache JMeter. JMeter tested the public endpoint so that the measured path included the workstation network route, Google Cloud VM, Nginx, Spring Boot, MySQL, and Redis where relevant.

The JMeter execution was divided into four groups:

| Group | Plans | Main parameters |
|---|---|---|
| Smoke | `01` to `08` | 1 thread, 1 loop |
| Read-only load | `01_homepage`, `02_product_list`, `03_product_detail` | 10, 50, 100, 200 threads |
| Authenticated load | `04_login`, `08_order_history` | 10, 50, 100 threads |
| Controlled mutation | `05_add_to_cart`, `06_place_order`, `07_simulated_payment` | 1, 5, 10 threads |

Mutation scenarios were intentionally limited to lower thread counts because add-to-cart, place-order, and simulated-payment tests modify live demo data such as cart rows, order rows, stock, and payment status.

### 5.6 Result Interpretation

The testing results support several conclusions.

First, the main system functions were testable and executable. Backend unit tests, frontend checks, build checks, database schema checks, and JMeter smoke tests all passed.

Second, the cloud deployment was sufficient for the FYP demonstration workload. Nginx, Spring Boot, MySQL, and Redis remained active after read-only, authenticated, and controlled mutation load phases.

Third, the JMeter testing satisfies the Network Technology requirement because it measures response time, P90, throughput, samples, errors, and error rate under different thread parameters. The tests were executed through the public endpoint, so the actual cloud request path was included in the measurement.

Fourth, the results must not be interpreted as commercial production capacity. The system still uses HTTP only, runs on a single VM, uses a shared demo account for mutation tests, and shows multi-second P90 response times for some high-load read scenarios.

### 5.7 Limitations of Testing Results

The testing results have the following limitations:

- the public endpoint uses HTTP, not HTTPS;
- the load generator ran from a local workstation, so Internet routing may affect latency;
- mutation tests use the same demo account and selected product variant;
- raw `.jtl` files and generated JMeter HTML reports are not committed to Git because they are large;
- the official results reflect VM and network conditions on 16 June 2026;
- security testing is limited to basic checks, not full penetration testing; and
- the results prove academic prototype suitability, not production capacity.

| JMeter was not available in the local shell at the beginning of testing. | Performance testing could not start immediately. | Apache JMeter 5.6.3 was downloaded, checksum-verified, and prepared under local ignored tooling. |
| Sandbox DNS could not resolve Apache download hosts. | JMeter download failed in the restricted environment. | Download was retried outside the sandbox with approval; SHA512 verification matched. |
| Sandbox blocked socket access to the public endpoint. | One-user homepage validation failed with `Operation not permitted`. | JMeter was rerun outside the network sandbox and validation succeeded. |
| Original JMX files used one thread and lacked sufficient assertions. | Load-test results would not be reliable enough for D7 evidence. | All eight plans were parameterized and business-response assertions were added. |
| Mutation tests changed live demo data. | Cart, order, stock, and sales records changed. | Mutation was limited to lower thread counts, MySQL backup was created, and data impact was recorded. |
| Some read scenarios showed multi-second P90 under high load. | The system is not suitable for commercial performance claims. | Results were interpreted as academic prototype evidence and future optimization items were identified. |

### 6.2 Summary of Testing Conducted

The testing phase for R Mall included unit testing, regression testing, integration testing, deployment testing, basic security testing, and Apache JMeter performance testing. Unit tests verified email verification logic, Redis TTL, cooldown, and password reset. Frontend checks verified authentication wiring, route guards, and production `/api` configuration. Database checks verified that the schema remained consistent with the system design. Deployment testing verified that the system was reachable through Google Cloud VM with Nginx as reverse proxy.

JMeter testing proved that all eight main user journeys could be executed through the public endpoint. In total, 3,197 JMeter sampler executions were summarized with 0 errors and an overall observed error rate of 0.00%. Read-only scenarios were tested up to 200 threads, authenticated scenarios up to 100 threads, and controlled mutation scenarios up to 10 threads.

In conclusion, R Mall satisfies the project purpose as a cloud-based small e-commerce prototype that can be tested from the Network Technology perspective. The system supports the main user functions and produces performance evidence suitable for the final project report. However, the system still has limitations in HTTPS, commercial scalability, production-grade security, shared-account mutation testing, and high-load response time.

### 6.3 Recommended Future Testing Improvements

Future testing improvements include:

- implement HTTPS and retest the endpoint after TLS certificate configuration;
- run longer soak tests to detect memory, connection, or database stability issues;
- prepare generated users and resettable seed products for cleaner mutation testing;
- run formal User Acceptance Testing with a checklist;
- run deeper security testing based on OWASP WSTG;
- profile database queries for product list and product detail endpoints; and
- collect CPU, RAM, disk I/O, and network I/O metrics during JMeter execution.
