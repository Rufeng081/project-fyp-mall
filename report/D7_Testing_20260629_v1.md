## 1. INTRODUCTION

### 1.1 Purpose of the Document

This D7 document reports the testing of R Mall, a cloud-based small e-commerce platform developed for a Network Technology Final Year Project. It explains the testing plan, test basis, selected testing techniques, test case design, execution procedure, testing results, problems encountered, and conclusion.

The purpose of this document is to show that the implemented system satisfies the main functional, deployment, and network-performance requirements defined in the D5 proposal and implemented in D6. The testing does not attempt to certify R Mall as a commercial production system. Instead, it evaluates whether the system is suitable for an academic cloud-based e-commerce demonstration and whether its network behaviour can be measured under controlled simulated user loads.

### 1.2 Scope of Testing

The testing scope covers three main areas:

1. Functional and regression testing for authentication, email verification, storefront flow, route protection, database schema, and production build readiness.
2. Deployment and connectivity testing for the Google Cloud VM, public HTTP endpoint, Nginx reverse proxy, Spring Boot backend, MySQL, Redis, and public API path mapping.
3. Network performance testing using Apache JMeter for smoke, read-only load, authenticated load, and controlled mutation scenarios.

The testing scope excludes real payment-gateway testing, security penetration testing, HTTPS performance comparison, long-duration soak testing, Docker/Kubernetes testing, autoscaling evaluation, and commercial capacity certification. These exclusions match the implementation boundaries stated in D5 v3 and D6 v2.

### 1.3 Relationship with Other Project Documents

This document is based on:

- D5 Proposal Report version 3, which defines the project objectives, scope, requirements, architecture, and performance-evaluation direction.
- D6 Implementation version 2, which explains the implemented frontend, backend, database, deployment, and JMeter test artefacts.
- Project verification workflow, phase reports, JMeter execution records, JMeter summary tables, source tests, and retained result charts.

D7 will later become part of Chapter 4, "System Development and Testing", in the D8 final project report.

### 2.3 Testing Approach

The testing approach combines automated and evidence-based testing. Backend tests use JUnit and Mockito to verify service-level behaviour. Frontend checks use Node.js scripts to inspect important route, authentication, and deployment wiring. Build tests confirm that the backend can be packaged and the frontend can be compiled. Deployment checks confirm that services remain active on the VM and that the public request path works through Nginx. JMeter tests simulate users against the public cloud endpoint and collect performance metrics.

For the Network Technology track, the most important testing approach is black-box HTTP testing through the deployed public endpoint. JMeter sends requests as an external client, and the measured response includes browser-facing HTTP access, Nginx forwarding, Spring Boot processing, and MySQL/Redis interaction where relevant.

**Table 2.3: Testing Types Used in This Project**

| Testing type | Purpose | Examples in this project |
|---|---|---|

| Integration testing | Verify that multiple application parts work together. | Login session creation, Redis-backed token storage, order creation, simulated payment. |
| Regression testing | Verify that previous features still work after changes. | Frontend auth check, route fallback check, deployment config check, database schema check. |
| Black-box functional testing | Verify externally visible behaviour without inspecting internal code during execution. | JMeter smoke tests for homepage, product list, login, cart, order, payment, and order history. |
| Deployment/connectivity testing | Verify network path and runtime service readiness. | Public homepage, public API path mapping, VM service health checks. |
| Performance/load testing | Measure response time, throughput, and error rate under concurrent users. | JMeter read-only, authenticated, and controlled mutation matrices. |
| Controlled mutation testing | Verify write flows while limiting data risk. | Add-to-cart, place-order, and simulated-payment JMeter scenarios at 1, 5, and 10 threads. |

### 3.3 JMeter Performance Test Case Design


## 4. TESTING EXECUTION

### 4.1 Execution Procedure

The retained official testing evidence was executed on 16 June 2026. The testing process followed this sequence:

1. Prepare JMeter 5.6.3 locally and verify the downloaded checksum.
2. Validate all JMeter XML files with `xmllint`.
3. Parameterise the JMeter plans with `THREADS`, `RAMP_UP`, and `LOOPS`.
4. Add sampler-level assertions so that valid business responses are checked.
5. Run one-user smoke tests for all eight JMeter plans.
6. Create a VM-side MySQL backup before mutation tests.
7. Record mutation baseline counts for `t_order`, `cart`, and selected product stock.
8. Check VM service health before load testing.
9. Run the read-only load matrix.
10. Check VM service health after read-only load.
11. Run authenticated load tests.
12. Check VM service health after authenticated load.
13. Run controlled mutation tests.
14. Record post-mutation database impact and VM service health.
15. Generate retained CSV, Markdown summary tables, and SVG charts.
16. Run final local and VM verification checks.

### 5.5 Database Impact of Mutation Tests

Mutation tests intentionally changed live cart, order, stock, and sales data. This was controlled by limiting mutation thread counts and creating a VM-side database backup before mutation execution.

**Table 5.4: Mutation Test Database Impact**

| Metric | Before mutation smoke/load | After smoke | After controlled mutation load |
|---|---:|---:|---:|
| `t_order` rows | 3 | 5 | 37 |
| `cart` rows | 3 | 4 | 25 |
| Chair stock | 500 | 499 | 483 |
| Paid orders | Not recorded in baseline table | 3 | 19 |
| Pending Payment orders | Not recorded in baseline table | 1 | 17 |

The stock reduction from 499 after smoke to 483 after controlled mutation load matches the 16 simulated-payment threads from the 1, 5, and 10 mutation matrix. Extra cart rows are expected because add-to-cart scenarios deliberately create cart data and the shared-account JMeter flow does not clean every cart item.

### 5.6 Interpretation

The testing results support four conclusions.

First, the main system functions were testable and executable. Backend tests, frontend checks, build checks, schema checks, and JMeter smoke tests all passed in the retained verification record.

Second, the cloud deployment was suitable for the selected FYP demonstration workload. Nginx, Spring Boot, MySQL, and Redis remained active after the read-only, authenticated, and mutation test phases.

Third, the JMeter results satisfy the Network Technology requirement to test a built network application under different parameters. The project varied thread counts across read-only, authenticated, and mutation scenarios and collected average response time, P90 response time, throughput, samples, errors, and error rate.

Fourth, the results must be interpreted within project limitations. The public endpoint used HTTP rather than HTTPS. The load generator ran from a local workstation, so internet route variability influenced response time. Mutation tests used a shared demo account and selected product variant, which is suitable for controlled FYP evidence but not for production order-concurrency certification.

## 6. SUMMARY

### 6.1 Unexpected Testing Problems and Resolutions

**Table 6.1: Unexpected Testing Problems and Resolutions**

| Problem | Effect | Resolution |
|---|---|---|
| JMeter was not installed in the local shell. | Performance testing could not start immediately. | Apache JMeter 5.6.3 was downloaded, checksum-verified, and extracted under ignored local tooling. |
| Initial sandbox DNS could not resolve Apache download hosts. | JMeter download failed inside the restricted sandbox. | Download was retried outside the sandbox with approval; SHA512 verification matched. |
| Sandboxed JMeter could not open public endpoint sockets. | A one-user homepage validation failed with socket permission errors. | JMeter was rerun outside the network sandbox; homepage validation passed. |
| Existing JMX files were fixed at one thread and mostly lacked business assertions. | Load-test results would not be reliable enough for D7 evidence. | All eight JMX plans were parameterised and sampler-level assertions were added. |
| Mutation tests modified live demo data. | Cart, order, stock, and sales records changed during testing. | Mutation tests were limited to lower thread counts; a VM-side MySQL backup was created; database impact was recorded. |
| Some high-load browsing scenarios had multi-second P90 response time. | The system cannot support broad commercial-scale performance claims. | Results were interpreted as academic prototype evidence and future optimisation items were identified. |

### 6.2 Testing Summary

This D7 document has described the testing plan, test basis, testing types, test case design, execution procedure, results, and limitations for R Mall. The project used automated backend tests, frontend verification scripts, build checks, deployment checks, and Apache JMeter performance tests. The retained official JMeter execution produced 3,197 sampler executions with 0 JMeter errors and an observed overall error rate of 0.00%.

The evidence shows that R Mall is functional and measurable as a cloud-based Network Technology FYP prototype. The system supports the required customer journey and provides performance evidence for response time, throughput, and error rate under controlled concurrent loads. The results also identify realistic limitations: HTTP-only deployment, single-VM capacity, shared-account mutation testing, and multi-second response times under some high-load browsing scenarios.

### 6.3 Future Testing Improvements

Future testing should include:

- HTTPS deployment testing after a domain and TLS certificate are configured.
- Separate HTTP-versus-HTTPS comparison only after HTTPS is implemented.
- Longer-duration soak testing to detect memory, connection, or database stability issues.
- More isolated mutation testing using generated users and resettable seed data.
- Additional browser-based user acceptance testing with a formal checklist.
- More detailed database query profiling for product list and product detail endpoints.
- Optional security testing for authentication, session handling, and public file routes.
