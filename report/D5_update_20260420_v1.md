[]{#_Toc220830833 .anchor}ABSTRACT

With the continuous growth of digital commerce, small e-commerce platforms increasingly rely on cloud-based deployment to improve accessibility, centralized management, and service availability. However, even for small-scale web applications, network performance remains an important concern because response time, throughput, and communication reliability directly influence user experience during login, product browsing, cart updates, and checkout activities. This project presents the development and network performance evaluation of a cloud-based small e-commerce platform. The system is designed as a web-based application that supports essential transaction functions, including user registration and login, product browsing, shopping cart management, order placement, and simulated payment confirmation. The platform is deployed on a cloud-based server and uses Nginx as a reverse proxy to manage incoming client requests, while the backend application and database support the core business workflow. From a Network Technology perspective, the project further examines the communication mechanisms involved in request transmission between the client, reverse proxy, application server, and database, with particular attention to HTTP and HTTPS communication in a cloud environment. To evaluate the developed platform, Apache JMeter is used to conduct performance testing under different parameters, including different numbers of concurrent users and comparisons between HTTP and HTTPS communication. The evaluation focuses on measurable indicators such as response time, throughput, and error rate. The expected outcome of this study is a practical undergraduate-level cloud computing application that combines successful system development with analysable network performance results, while also providing a useful reference for the design and evaluation of small cloud-hosted web platforms in the context of Network Technology.

**Keywords:** Cloud-Based Application, Small E-Commerce Platform, Network Performance Evaluation, HTTP/HTTPS, Reverse Proxy, Nginx, Cloud Computing.

[]{#_Toc220830840 .anchor}The rapid development of the digital economy has made e-commerce an important platform for modern business activities. Today, even small online stores require stable web access, efficient request handling, and reliable communication between users and cloud-hosted servers. As more web systems are deployed in cloud environments, the performance of network communication becomes increasingly important because it directly affects user experience during browsing, cart updates, and checkout activities.

For small e-commerce platforms, cloud deployment offers practical advantages such as accessibility, centralized hosting, and easier system management. However, the performance of a cloud-based web application is not determined only by its business functions. It is also influenced by the way requests are transmitted through the network, how the server processes those requests, and how supporting components such as reverse proxies and databases respond under different usage conditions. In particular, communication through HTTP and HTTPS may introduce different processing overheads, while the use of a reverse proxy such as Nginx may affect traffic handling efficiency.

In the context of Network Technology, these issues are important because a web application can also be studied as a communication system involving multiple layers, including the client browser, reverse proxy, application server, and database server. Therefore, the evaluation of a cloud-based e-commerce platform should not focus only on functional correctness, but also on measurable network-related performance indicators such as response time, throughput, and error rate.

Based on this context, this project is titled "Development and Network Performance Evaluation of a Cloud-Based Small E-Commerce Platform." The project aims to develop a small but complete e-commerce web application and deploy it in a cloud environment, while also evaluating its network performance under different test settings. Rather than focusing on large-scale infrastructure, the project emphasizes a feasible undergraduate-level implementation that combines application development with practical performance analysis. This direction is more consistent with the Network Technology requirement to build an application, test it, analyze its results, vary parameters, and study protocol usage in practice.

2.  Problem Statement

Description of the problem: Despite the increasing reliance on cloud-hosted and containerized deployments, the performance of e-commerce applications in resource-limited environments remains highly unpredictable under peak concurrent traffic and external payment-service dependency. The combined effects of internal service-network bottlenecks and wide-area network (WAN) overhead from third-party APIs can cause unstable latency, reduced throughput, and elevated error rates. Specifically, the challenges facing the current infrastructure are fourfold:

First, **Inefficiency of Traditional Monolithic Deployment:** Traditional e-commerce platforms typically rely on monolithic architectures deployed on physical servers or heavyweight Virtual Machines (VMs). Under this architecture, expansion to cope with sudden surges in network traffic (such as promotional peaks) is slow and computationally expensive due to the inherent overhead of hardware virtualization.

VMs require a significant amount of system resources to maintain independent Guest Operating Systems, leading to resource contention that reduces the CPU cycles and I/O bandwidth available for packet processing. This inefficiency directly correlates with increased network communication delays and response latency under system load, ultimately resulting in a severe decline in the Quality of Service (QoS) for end users.

Second, **Network Congestion and Single Point of Failure:** In simplistic deployment schemes lacking a high-performance Reverse Proxy or Ingress Controller, all incoming network traffic converges on a single application entry point. This architecture creates severe bottlenecks at the transmission layer. When the application server is overwhelmed by a large volume of concurrent TCP connections, it frequently exhausts available file descriptors or ephemeral ports, resulting in packet loss and connection timeouts (RST packets). Furthermore, without an optimized traffic distribution strategy---such as the Layer 7 load balancing provided by Nginx---requests cannot be effectively routed or cached at the network edge. This deficiency leads to redundant data transmission and bandwidth saturation, significantly increasing the load on back-end servers and potentially causing service unavailability due to connection saturation, request queue buildup, and elevated timeout rates.

Third, **Latency Uncertainty in Third-Party API Integration:** Modern distributed e-commerce systems increasingly rely on external Wide Area Network (WAN) communication for critical functions, particularly secure payment processing (e.g., Alipay Sandbox) and OAuth 2.0 authentication. The primary challenge here is the \"uncontrollable\" network uncertainty introduced by these external dependencies. Unlike internal Local Area Network (LAN) interactions, communication with sandbox APIs involves complex overheads, including DNS resolution time, variable routing paths through the public internet, and the latency of Synchronous Blocking Calls during SSL/TLS handshakes. These factors introduce high-latency variables that are difficult to predict, yet they directly impact the total transaction time experienced by the user.

Fourth, **Lack of Empirical Performance Quantification:** While cloud-native tools like Docker and Nginx are widely used, there is a notable lack of empirical research that specifically quantifies their performance limits in **resource-constrained** cloud environments (e.g., entry-level instances). Most existing literature focuses on functional implementation rather than rigorous stress testing. There is a gap in understanding how the integration of high-latency external APIs affects the overall Throughput (TPS) of a containerized microservice architecture. This highlights a critical need for a controlled experimental setup using tools like Apache JMeter to isolate and measure internal vs. external network bottlenecks under reproducible high-concurrency scenarios.

3.  []{#_Toc220830841 .anchor}Proposed Solution

To address the latency bottlenecks and architectural inefficiencies identified in the Problem Statement, this project proposes a comprehensive solution titled \"Implementation and Performance Evaluation of a Secure Containerized Infrastructure.\" This solution is composed of three integrated layers: a containerized microservice host, a high-performance secure ingress gateway, and a rigorous quantitative benchmarking framework.

Containerized Architecture Implementation (Docker) To overcome the I/O overhead and heavy resource consumption of traditional hypervisor-based virtualization, this project utilizes Docker to implement a lightweight containerized network architecture. Unlike Virtual Machines, Docker employs operating system-level virtualization, allowing the e-commerce application (Spring Boot) and persistence layers (MySQL, Redis) to share the host kernel while maintaining strict process isolation (Namespaces and Cgroups). Crucially, the solution leverages the Docker Bridge Network to create an internal software-defined network. This configuration allows inter-container traffic to be routed directly through the kernel's network protocol stack (via virtual Ethernet pairs, veth), minimizing the packet processing overhead associated with external physical routing. This approach significantly reduces \"cold start\" latency and optimizes the utilization of limited cloud hardware resources.

Secure Reverse Proxy and Ingress Management (Nginx) To mitigate the risks of network congestion and single-point failures, Nginx is deployed as the high-performance Ingress Controller and Reverse Proxy. Utilizing an asynchronous, event-driven architecture, Nginx is capable of handling thousands of concurrent TCP connections with minimal memory footprint compared to thread-based servers like Apache. In the proposed topology, Nginx functions as the centralized Secure Gateway for all incoming HTTP/HTTPS traffic. Key network functions include:

TLS Termination: Offloading SSL/TLS decryption overhead from backend application containers to the edge, thereby improving backend CPU efficiency.

Load Balancing: Implementing the Round Robin algorithm to evenly distribute incoming requests across multiple application instances, ensuring high availability.

Static Content Caching: Serving static assets from the edge to reduce internal bandwidth consumption and hide the internal network topology from the public Wide Area Network (WAN).

Hybrid Network Integration and Performance Analysis Framework Recognizing the system\'s dependency on external services, the solution integrates a Hybrid Network Strategy. Secure communication channels (HTTPS) are established to interact with the Alipay Sandbox (for payment simulation) and WeChat OAuth 2.0 (for authentication), introducing realistic WAN latency variables into the testbed. To quantify the efficiency of this architecture, a rigorous Performance Analysis Framework is built using Apache JMeter. Acting as a programmable traffic generator, JMeter will simulate varying levels of network pressure (ranging from 100 to 500 concurrent threads) to stress-test the infrastructure. In this study, a JMeter thread represents one concurrent virtual user (VU). Test configurations will explicitly specify ramp-up time, steady-state duration, and HTTP connection reuse (keep-alive) to ensure repeatability and comparability across concurrency levels.

This evaluation phase aims to generate empirical data for critical Quality of Service (QoS) metrics---specifically End-to-End Latency (RTT), Throughput (TPS), and Request Failure Rate (HTTP errors, timeouts, and connection failures). Crucially, the analysis is designed to distinguish between the \"uncontrollable\" network cost of external WAN interactions and the \"controllable\" processing time of the internal LAN, providing data-driven insights for optimizing cloud-hosted architectures.

Proposed Development Process Model: Iterative Incremental Development (IID) This project adopts the Iterative Incremental Development (IID) methodology to guide the lifecycle of the network architecture design and implementation. Configuring a containerized topology involving Docker networking, Redis caching, and Nginx routing requires precise integration. IID provides Fault Isolation---if a network connection failure (e.g., a Docker container port conflict or DNS resolution error) occurs, it can be identified and resolved within the current iteration. This prevents architectural errors from compounding, significantly reducing the risk of catastrophic failure during the final integration of external APIs.

Adaptability for Performance Tuning Furthermore, this model is critically selected to support the project's core objective of Quantitative Performance Analysis. Network optimization is not a singular event but a cyclical process of benchmarking and tuning. The iterative approach establishes a \"Test-Analyze-Tune\" feedback loop. For instance, initial stress tests may reveal unacceptable latency after adding the SSL layer, prompting a specific iteration focused solely on optimizing Nginx's Keep-Alive settings or Redis caching strategies. This continuous integration of testing ensures that the final performance data reflects a tuned and stable environment, rather than a raw, unoptimized prototype.

2.  []{#_Toc220830856 .anchor}Existing Systems and Technologies

To understand the principle behind the selected technology stack (Docker, Nginx, Spring Boot), it is necessary to critically analyze the existing industry standards and their alternatives from the perspective of network performance.

At present, the industry relies heavily on virtualization technology to maximize hardware utilization, but there is an essential difference between virtual machines (VM) and Docker containers. Virtual machines are managed by hypervisors (such as VMware and KVM), which simulate a complete hardware stack for each instance. Research shows that this kind of simulation will lead to excessive resource occupancy and reduced network throughput due to additional abstraction layers. In contrast, the Docker container uses the Linux kernel features of the host, especially the namespace and Cgroups, to isolate the process. This lightweight method allows more direct interaction with the network interface of the host. Theoretically, it can provide higher throughput (TPS) and lower latency for e-commerce transactions, which is why this study chooses Docker containers.

In terms of Web server architecture, the choice of gateway is crucial for handling network traffic. Apache HTTP server has always occupied a dominant position with its modular characteristics. However, its process-based architecture (assigning a thread to each request) can cause a serious bottleneck in the case of high concurrency - this phenomenon is called the C10K problem. The Nginx used in this project adopts an event-driven asynchronous architecture. Existing literature confirms that Nginx performs significantly better than Apache as a reverse agent and load balancer, and can handle thousands of concurrent connections with minimal memory footprint. This feature makes it ideal for analyzing high-concurrency network performance in resource-limited environments.

Modern e-commerce infrastructures commonly rely on transport-layer encryption and federated identity protocols to protect user data and transactions. However, these mechanisms introduce measurable performance costs. TLS/HTTPS adds cryptographic overhead and handshake latency, particularly under short-lived connections without session resumption or keep-alive. OAuth 2.0 and OpenID Connect flows may further introduce additional redirects and callback interactions, increasing end-to-end round trips. When such secure interactions involve third-party services over the public Internet, WAN variability (DNS resolution, routing changes, and server-side response time) becomes a dominant factor affecting observed latency and throughput. Therefore, performance evaluations of high-concurrency e-commerce systems should explicitly account for security-related overhead and distinguish it from internal service processing time.

4.  []{#_Toc220830858 .anchor}Methodology in Past Studies

    1.  []{#_Toc220830859 .anchor}Research Approaches Used

A systematic review of previous literature shows that researchers mainly use two different methods to analyze network performance: analytical modeling and simulation-based testing.

Early research usually relied on mathematical modeling, especially queuing theory (such as M/M/1 or M/G/1 queuing model), to predict the response time of the server under load. These analytical methods focus on the theoretical limits of throughput derived from fixed variables. In recent years, discrete event simulation (DES) tools (such as NS-2, OPNET or OMNeT++) have become standard tools. Researchers use these platforms to virtually model complex network topologies, so that they can adjust bandwidth and packet loss parameters in a controlled software environment. In terms of deployment, previous practical research usually uses tools such as Apache Bench (ab) or LoadRunner to generate synthetic HTTP traffic for locally hosted virtual machines (VMs) to measure the basic request-response cycle.

2.  []{#_Toc220830860 .anchor}Effectiveness and Weaknesses of Methodologies

Although analytical models and simulations are cost-effective and scalable, there are significant limitations when applied to modern cloud native environments. A major weakness is the dependence on idealized conditions. Simulation tools usually fail to capture the \"noise\" in the real operating system, such as CPU overhead caused by Docker Network Address Translation (NAT) or context switching in the Linux kernel.

In addition, a key limitation of the previous methodology is the lack of authenticity of the wide area network. Research conducted in a local area network (LAN) or local host environment often ignores the impact of wide area network (WAN) latency. They cannot accurately reflect the unpredictability of third-party API calls (such as payment gateways), which is the key bottleneck in the actual e-commerce system.

    1.  []{#_Toc220830863 .anchor}Comparison of Technologies

Previous research in the field of Web application hosting mainly adopted hypervisor-based virtualization technology (virtual machine) and thread-based Web servers, such as Apache. However, the comparative analysis of modern literature shows that the field is undergoing a significant shift to containerization and event-driven architecture. In terms of resource efficiency, virtual machines (VMs) are generally considered resource-intensive because each instance requires a complete customer operating system, resulting in a large amount of memory and storage overhead. In contrast, containerization technology, especially Docker, uses the namespace of the host kernel to reduce the mirror size from GB level to MB level. This fundamental difference enables cloud instances to achieve higher density, making containers more cost-effective solutions for budget-limited network deployments.

In addition, when comparing the Web server architecture, the traditional thread-based server will assign a dedicated thread to each client connection. Although this model runs stably, it has poor scalability under high load due to the overhead of context switching. On the contrary, the asynchronous event-driven server (such as Nginx) used in this study can handle multiple connections in a single thread. Comparative research shows that Nginx is significantly superior to Apache in handling concurrent connections and has extremely low memory occupancy, so it is ideal for analyzing high-throughput network scenarios (Kleftakis et al., 2022).

1.  []{#_Toc220830864 .anchor}Critique of Past Studies

Although the existing literature has laid a solid foundation for the development of e-commerce, some key defects limit the applicability of its research results in the actual cloud environment. A major limitation is the dependence on the \"local host\" test environment. A considerable part of academic projects deploy and test applications on the local loopback interface, which effectively eliminates network latency (round trip time) and packet loss. Such research cannot reflect the performance of the real world, because the traffic does not pass through the physical network protocol stack and will not encounter real bandwidth restrictions.

In addition, many previous studies have significant shortcomings in the specific indicators of the network. Research often focuses too much on user experience (UX) indicators, such as page loading speed or functional correctness, while ignoring key network-level indicators, such as TCP connection time, handshake delay, and throughput stability under pressure. Without these quantitative network indicators, it is difficult to distinguish whether the performance bottleneck comes from the application logic or the underlying network infrastructure (Yadav et al., 2018).

1.  []{#_Toc220830878 .anchor}Requirements Elicitation Methodology

Before defining the specific stakeholder needs, it is essential to establish the evidence-based methodology used to determine the system's scope. The requirements for this project were not arbitrarily selected; instead, they were derived using a hybrid approach: a Goal-Oriented Requirements Engineering (GORE) perspective supported by a Needs Assessment Survey.

1.  []{#_Toc220830879 .anchor}Survey-Based Bottleneck Identification

To ensure the proposed infrastructure aligns with real-world industry pain points, a technical survey was distributed to a focus group of 15 IT professionals (including Network Engineers, DevOps Specialists, and Backend Developers). The survey results (refer to Appendix A for the full questionnaire) highlighted two primary technical challenges (Zhu, 2018):

Network Latency Sensitivity: 80% of respondents identified \"latency accumulation\" across service boundaries as the most critical factor affecting user retention during high-traffic events.

Integration Complexity: The majority of respondents emphasized that securely integrating third-party payment gateways (e.g., Alipay) creates the highest risk of transaction failure due to network timeouts.

2.  []{#_Toc220830880 .anchor}Scope Refinement using GORE

Based on the survey findings, the GORE methodology was applied to refine the project scope. Instead of building a feature-rich e-commerce store, the system scope is restricted to the \"Golden Path\" of E-commerce Transaction:

Selected Flow: User Authentication (OAuth 2.0) → Product Browsing → Order Creation → Secure Payment (Alipay).

Justification: This flow constitutes the dominant transaction pattern responsible for generating network load.

Exclusions: Features such as user reviews, wishlists, or complex administrative dashboards were explicitly excluded. While functionally useful, they contribute marginally to the network stress tests required for the project\'s core performance evaluation objectives.

2.  []{#_Toc220830881 .anchor}Stakeholder Analysis and User Needs

Following the scope refinement in Section 3.2, the system requirements are further categorized by stakeholder roles. To ensure the system satisfies both the research objectives and operational realism, needs are derived from two distinct perspectives: the End-User (Shopper) and the Network Administrator (Researcher)

The End-User role defines a realistic transaction flow that generates representative workload patterns, while the Researcher role defines the controllability and observability necessary for repeatable performance experiments. Together, these needs ensure that the testbed can reproduce the \"Golden Path\" reliably and produce measurable outcomes for latency, throughput, and failure behaviour under stress.

1.  []{#_Toc220830882 .anchor}End-User (Shopper) Needs

From the Shopper's perspective, the system must provide a seamless and responsive transactional experience. Authentication should be frictionless and secure, avoiding lengthy registration while establishing a trusted session through WeChat OAuth 2.0. Product browsing should return timely feedback with minimal perceived latency, particularly for retrieval of product metadata and associated media. Finally, the checkout stage must support secure payment processing through a recognized gateway (Alipay Sandbox), ensuring that payment-related exchanges are transmitted safely across the Wide Area Network (WAN) while maintaining a predictable end-to-end experience.

2.  []{#_Toc220830883 .anchor}Network Administrator (Researcher) Needs

From the Researcher's perspective, the system must behave as an observable network entity and a controllable experimental platform. Incoming traffic must be governed through an ingress layer (Nginx reverse proxy) to support connection management, request routing, and the generation of access logs suitable for quantitative analysis. The infrastructure must sustain high-concurrency workloads generated by tools such as Apache JMeter, enabling measurement of response stability, throughput trends, and failure behaviours (timeouts/errors) as concurrency increases.

In addition, the Researcher must be able to scale backend application instances horizontally (e.g., increasing container replicas) to evaluate how scaling impacts throughput and latency under fixed resource constraints. The methodology must therefore ensure that key test variables---concurrency level, request flow, ramp-up behaviour, and connection reuse settings---can be configured and reproduced across repeated test runs.

1.  []{#_Toc220830886 .anchor}Non-Functional Requirements (Quality Attributes)

As this study is positioned within Network Technology, non-functional requirements define the measurable quality constraints used to judge the system's fitness as a performance testbed. These constraints are expressed as baseline and stress targets to support repeatable measurement and clear acceptance criteria.

For baseline performance (NFR-01), under a workload of 100 concurrent virtual users, the end-to-end response time along the critical transaction path (Login → Browse → Place Order → Payment initiation) shall achieve a 95th percentile (P95) of no more than 2000 ms, measured over a continuous 10-minute window using Apache JMeter. "Success" for this baseline target is defined as HTTP 200 responses with valid business payloads and successful completion of the intended step (e.g., token issued for login, order created for checkout).

For stress capacity (NFR-02), the system shall maintain stable service behavior under 500 concurrent TCP connections for a continuous 10-minute stress window. During this stress scenario, the error rate shall remain at or below 0.1%, where errors include connection drops, timeouts, and non-2xx HTTP responses that prevent completion of the requested operation. These thresholds are intended to highlight bottlenecks attributable to reverse proxy routing, container networking, and external WAN dependencies, rather than to feature-level application complexity.

For scalability (NFR-03), the architecture shall support horizontal scaling by adding new Docker container instances without redesigning the system. The Nginx routing configuration shall allow straightforward inclusion of additional upstream endpoints so that comparative tests can be conducted across different scaling levels.

2.  []{#_Toc220830887 .anchor}Hardware and Software Requirements

To support reproducibility and to ensure that measured results reflect network behavior under constrained conditions, the project specifies separate environments for development and deployment. Development activities are conducted on a local workstation, while performance analysis is executed on a cloud instance configured as an edge-like node.

In the development environment, the workstation is expected to provide an Intel i5/i7-class CPU and 16 GB RAM, supporting iterative backend development and container-based integration testing. The software stack includes IntelliJ IDEA for implementation, Docker Desktop for local container management, and Apache JMeter 5.5 for initial load script preparation.

In the deployment (cloud) environment, the system is hosted on an Ubuntu 20.04 LTS instance with deliberately constrained resources (2 vCPU and 2 GB RAM) to expose potential bottlenecks. The network stack uses Nginx 1.18 as the Layer-7 reverse proxy and Docker Engine 20.10 to provide the container runtime and internal bridge network (docker0).

3.  []{#_Toc220830888 .anchor}Network Requirements (OSI Model Specification)

The protocols involved in system communication are specified using the Open Systems Interconnection (OSI) model to clarify how data is transported between clients, the reverse proxy, containerized services, and external gateways (Fielding & Reschke, 2014).

At Layer 7 (Application), the system uses HTTP/1.1 for RESTful API communication and HTTPS (TLS 1.2) for secure external handshakes with WeChat OAuth 2.0 and Alipay Sandbox. Payloads are represented in JSON to support standardized parsing and efficient transport. At Layer 4 (Transport), TCP provides reliable delivery, and the reverse proxy is configured to leverage persistent connections (Keep-Alive) to reduce repeated handshake overhead between the proxy and backend containers. At Layer 3 (Network), IPv4 is used for routing. Internally, containers are assigned private IP addresses (e.g., 172.17.0.x) on a Docker bridge network, isolating inter-service traffic from the public WAN while enabling controlled routing through the proxy.

5.  []{#_Toc220830895 .anchor}Architecture Design

The architectural design of the proposed system is driven by two coupled objectives: (i) providing a minimal yet correct "Golden Path" e-commerce transaction flow, and (ii) enabling measurable and repeatable network performance evaluation under high concurrency. Unlike traditional monolithic deployments that tightly couple presentation, business logic, and persistence within a single runtime boundary, this project adopts a hybrid strategy. At the application level, a layered Model--View--Controller (MVC) structure is used to separate responsibilities and support fine-grained profiling. At the infrastructure level, a containerized network architecture is implemented to create an isolated, reproducible testbed in which ingress routing, internal service communication, and external WAN interactions can be instrumented and benchmarked under resource-constrained cloud conditions (2 vCPU, 2 GB RAM).

1.  []{#_Toc220830896 .anchor}Application Architecture: Layered Model--View--Controller (MVC)

To satisfy the functional requirements of the "Golden Path" transaction flow (Login → Browse → Place Order → Payment Initiation/Callback), the internal software structure follows a layered MVC pattern. This choice is strategic for performance evaluation: by decoupling request handling, business orchestration, and data access, the system can distinguish database I/O latency from application processing time, and separate internal processing costs from external WAN-dependent delays (e.g., OAuth token exchange and payment gateway interactions) (Necula, 2024).

The system is decomposed into three logical layers:

The Presentation/Controller Layer: This layer is the entry point for HTTP(S) requests forwarded by the Nginx reverse proxy. It performs request routing, basic validation, payload parsing, and response formatting (JSON), thereby providing a stable interface for benchmarking endpoints.

The Service/Business Logic Layer: This layer encapsulates the core transactional logic, including session establishment via WeChat OAuth 2.0, order state transitions, and payment initiation workflows. Security-relevant validations that affect correctness and timing behavior (e.g., OAuth state validation and payment callback verification) are enforced here to ensure that performance measurements are obtained under realistic secure interaction constraints.

From an interaction standpoint, the major data flows include:

1.  []{#_Toc220830898 .anchor}Network Topology Design

For a Network Technology project, the logical arrangement of network nodes and addressing boundaries is a primary determinant of measurable performance. Because the physical topology is abstracted by the cloud provider, this design focuses on the logical topology and software-defined segmentation implemented within the cloud host.

The topology is designed to approximate a production-style segmented deployment in which a public-facing ingress zone mediates access to a private internal service network. Docker's bridge network driver is used to create a private subnet (e.g., 172.17.0.0/16) hosting the containerized services, while the cloud host's public interface receives WAN traffic from clients and external callback sources.

Key design elements include:

**Cloud Host Interface (Public Zone):** The cloud instance exposes a public IP address to receive internet traffic from client browsers and benchmarking tools, as well as inbound webhook callbacks. Only necessary ingress ports are exposed at the host boundary (commonly 80/443), with all internal service ports kept non-public to reduce attack surface and to maintain controlled measurement conditions. *(Public IP shown in the diagram is for documentation only.)*

**Docker Bridge Network (Private Zone):** A private virtual subnet is established for inter-container communication. Containers receive internal IP addresses (e.g., 172.17.0.2--172.17.0.4) and communicate over the host kernel's virtual networking stack. This segmentation ensures that internal traffic remains isolated from the WAN while still traversing realistic routing constructs such as NAT and port mapping at the ingress boundary.

**Nginx Container (Ingress Gateway):** The Nginx container is the only container mapped to the host's public ports and serves as the reverse proxy gateway. It proxies requests to the application service over the internal network, enabling centralized ingress control, request distribution, and logging for performance analysis.

**Application Container (Internal Service Node):** The application service exposes its service port (8080) only within the internal bridge network. This prevents direct external access and ensures that all traffic is mediated by the ingress gateway, making measured RTT include proxy forwarding and internal routing overheads.

**Database Container (Internal Persistence Node):** The MySQL container accepts connections only from the application container (3306) over the internal network. This isolates persistence access and supports controlled evaluation of database-related latency under concurrency.

This topology is essential to the study because it forces requests to traverse the full deployment stack---public ingress, reverse proxy forwarding, container routing, and internal persistence---thereby ensuring that measured latency and throughput reflect realistic architectural overheads rather than simplified localhost-only behavior.

1.  []{#_Toc220830902 .anchor}Algorithm Design

The algorithmic complexity of the proposed system is primarily concentrated in the processing of asynchronous network events, specifically the payment gateway callback (webhook) that arrives from the Wide Area Network (WAN). Unlike synchronous API calls, webhook traffic is externally initiated, may be duplicated, and is subject to unpredictable WAN conditions (variable delay, retransmission, and burst arrival). Therefore, the system implements a strict "Check--Then--Calculate--Commit" algorithm to ensure that performance metrics are recorded only for valid, cryptographically verified packets, and that order state transitions remain correct under high concurrency.

From a Network Technology perspective, this algorithm serves two methodological purposes:

**Security correctness**: Preventing invalid or tampered callbacks from polluting the dataset (aligned with SR-03 and SR-01 in Section 3.3.5).

Measurement validity: Ensuring that latency/overhead measurements are generated in a consistent and repeatable manner, even when callbacks are duplicated or arrive out of order (aligned with the telemetry schema defined in Section 3.6).

1.  []{#_Toc220830903 .anchor}Core Algorithm: Secure Callback Verification, Idempotency, and Telemetry Capture

The algorithmic complexity of the proposed system is primarily concentrated in the processing of asynchronous network events, specifically the payment gateway callback (webhook) that arrives from the Wide Area Network (WAN). Unlike synchronous API calls (e.g., product browsing) where the control flow is initiated by the internal client, webhook traffic is externally initiated by the Alipay Sandbox Gateway. This inversion of control introduces significant non-deterministic variables: packets may be duplicated due to network retransmission policies, arrive out of order, or be subject to unpredictable WAN conditions (variable delay, jitter, and burst arrival). Furthermore, as these callbacks travel over the public internet, they represent a high-risk attack surface where malicious actors could attempt replay attacks or payload tampering to simulate fraudulent payment confirmations (Fett et al., 2016).

To mitigate these risks while ensuring precise performance measurement, the system implements a strict "Check--Then--Calculate--Commit" algorithmic strategy. This strategy is designed to decouple the security verification layer from the business logic layer, ensuring that system resources (such as database write locks) are not consumed by invalid requests.

Algorithm 3.1 describes the procedure executed by the PaymentListener module when the payment gateway webhook is received through the public ingress (Nginx). The algorithm performs three sequential tasks:

**Security Verification**: Validate the callback signature (e.g., RSA verification) before accepting the request.

**Idempotency Control**: Prevent double-processing when callbacks are duplicated or retried.

**Telemetry Capture**: Compute WAN-dependent delay and internal container processing overhead, then write an append-only telemetry record for analysis.

**Notes on measurement definitions and validity**

wan_latency_ms in this study is treated as a WAN-dependent delay indicator, computed from the difference between the external gateway timestamp (T_gateway) and the local ingress time (T_ingress). Because clock skew may exist between the gateway and the cloud host, the metric is interpreted comparatively (e.g., distribution shifts and percentile changes across workloads) rather than as an absolute physical propagation delay.

docker_process_ms approximates the internal processing overhead attributable to application-layer handling (verification + DB operations) within the containerized environment, which supports separation of internal vs. external delay contributions during analysis.

The telemetry insert is intentionally append-only to preserve traceability during stress tests; multiple callbacks for the same order may generate multiple telemetry rows, enabling error and duplication analysis.

As shown in [Figure 3.10](#_Ref220701129), the behavior can be explained in three phases:

**Phase 1: Transaction Initiation (Internal LAN / Container Network)** The client sends an order creation request to the public ingress. The Nginx gateway forwards the request to the Spring Boot service, which persists the order as PENDING in MySQL and returns a payment URL (or redirection instruction).

**Phase 2: External Processing (WAN Dependency)** The user performs payment confirmation through the external payment system. This phase introduces WAN variability and external processing time that cannot be controlled by the local infrastructure.

**Phase 3: Asynchronous Callback (Metric Capture + Verification)** The payment gateway sends a signed webhook to the public ingress. The system verifies the signature, enforces idempotency, and records telemetry (wan_latency_ms, docker_process_ms, and pkt_status) into Network_Trace_Log. The callback is acknowledged with HTTP 200 to prevent repeated retransmission from the gateway.

By explicitly modeling the out-of-band webhook loop, the system ensures that both security verification and network measurement remain consistent under high concurrency, supporting reliable interpretation of throughput, latency, and error behavior in subsequent evaluation chapters.
